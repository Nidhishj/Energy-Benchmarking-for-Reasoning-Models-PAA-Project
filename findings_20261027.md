| transformers | 4.57.1 | 4.57.1 | 4.57.1 | not stated (`>=4.20`) |

- Only `/scratch/nidhish/envs/energy` was upgraded; the old package list is `/scratch/nidhish/envs/energy_before_torch28_20261026.txt`.
- The cu128 build runs on driver 560: it has no Ada-specific (sm_89) code and uses its RTX 30-series (sm_86) code, which runs on the Ada.
  Checked: GPU visible, NVML, BF16, Qwen3-8B generates correct output.

**Effect of torch 2.8, same card (GPU 1), every matched measurement:**

| | Matched measurements | Energy 2.8 ÷ 2.6 (median) | Time 2.8 ÷ 2.6 | Power |
|---|---|---|---|---|
| B3-short (Qwen3-8B) | 78 | 1.03 (0.94–1.13) | 1.05 | same |
| B1 (BERT) | 17 | 1.04 | 1.04 | same |

So the newer software changes the results by about +3%, which is within the 1–9% difference between sessions. **Software versions do not
explain the Ada vs PRO 5000 gap (Issue 9), nor the gap to CLEAR's %Capture.**

**Where the time goes instead (BERT block, 64 tokens, profiler):** 338 µs per call (torch 2.6) / 316 µs (2.8), of which the GPU computes
only 46 µs (39 kernels); the GPU is busy ~14% of the time and waits for the CPU the rest. On the PRO 5000 the same call took 110 µs.
The remaining suspect for the Ada/PRO 5000 difference is the machine (CPU), not the CUDA/torch version.

### 4.3 Splitting each gap into time and power (B1, torch 2.8, 8 tokens)

| Gap | Parts | Whole | Energy | Time | Power | What is missing |
|---|---|---|---|---|---|---|
| Parts → block | attention + FFN int. + FFN out = 17.38 mJ | block 21.59 mJ | 80.5% | 244 vs 298 µs (81.9%) | 72 W both | **Time**: code that runs only inside `BertLayer.forward` (mask handling, `apply_chunking_to_forward`, output tuples); GPU waits, powered on |
| 12 × block → 12 in sequence | 12 × 298 µs at 72 W | 3,527 µs at 81 W | – | same | **72 → 81 W** | **Power**: one layer (14 MB) stays in the 96 MB L2 cache when repeated; 12 layers (170 MB) do not |
| Sum → full model | 3,726 µs | 3,923 µs | 83.5% (CLEAR way) | 95% | 72–81 → 84 W | **Time** (~200 µs: mask, positions, passing outputs) and power |

### 4.4 CLEAR Table 8: LayerNorm counted twice in the block check only

In Hugging Face BERT, `attention` (= `BertAttention`) contains `BertSelfOutput.LayerNorm` (LN 1), and `output` (= `BertOutput`) contains LN 2
(their own comment, `module_measure.py` line 114: "dense + residual + layernorm"). Table 8 adds a separate LayerNorm row on top:

| Table 8, BERT, 8 tokens | mJ |
|---|---|
| Attention (incl. LN 1) + FFN int. + FFN out (incl. LN 2) | 21.385 → 71.8% of block 29.802 |
| + separate LayerNorm row (LN 1 + LN 2 again) | +6.216 → 27.601 = their printed Captured(Block) → **92.6%** |

- This affects **only %Capture(Block)**. %Capture(Model) = 12 × block (measured whole) + embedding + head = 387.2 mJ → 96.7% does not use the parts.
- Table 12 (32–128 tokens) and the released code have no separate LayerNorm row.
- Our run shows the same pattern: 80.5% with each LN once, 87.5% with the extra row.

| 8 tokens, mJ | CLEAR paper | CLEAR's released code, our Ada | Our code, Ada, torch 2.8 |
|---|---|---|---|
| Block | 29.8 | 21.6 | 21.6 |
| Embedding | 5.9 | 6.0 | 5.6 |

**Questions for the authors:**
1. The exact BERT script for Tables 8 and 12, especially how the CLS/LM head and the block were measured.
2. torch, transformers, CUDA and driver versions; CPU.
3. In Table 8, does "Attention" include `BertSelfOutput`'s LayerNorm?
4. Were the parts measured in one process or separately; with warm-up and `torch.cuda.synchronize()`?

## 5. Idle power: what CLEAR says, and what we measured

CLEAR (section 3) treats idle energy as noise: repeating a part N times *"scales the effective runtime so that the total energy of the
repeated executions dominates the idle background consumption"*, and Eq. 4 gives E_c ± ε/N. They never measure or subtract idle.
We measure idle for 30 s at the start of each session and report it without subtracting (`baselines.md` line 71).

`b1/idle_test.py` on GPU 0 (free), BERT block, 8 tokens, torch 2.8:

**(1) Per-call energy vs N**

| N | 300 | 1,000 | 3,000 | 10,000 | 30,000 |
|---|---|---|---|---|---|
| Window | 0.10 s | 0.32 s | 0.94 s | 3.13 s | 9.34 s |
| mJ per call | 23.4 | 20.2 | 19.6 | 20.2 | 20.9 |
| Power | 66 W | 63 W | 63 W | 65 W | 67 W |

From N = 1,000 on, the per-call energy is constant. Repetition removes the **reading error** (only the 0.1 s window is off), but nothing that is
proportional to time can shrink with N.

**(2) Power of the GPU awake vs asleep**

| State | Power |
|---|---|
| Idle before any work (210 MHz SM, 405 MHz memory) | 27 W |
| One tiny kernel every ~300 µs: almost no work, but clocks at 2,505 / 10,000 MHz | **62 W** |
| Tiny kernel back to back | 75 W |
| **BERT block, 8 tokens** | **63–67 W** |
| Idle, first 15 s after the work (clocks still high) | 41 W |
| Idle, 15–45 s after | 15 W (below the 27 W `nvidia-smi` showed; the counter likely lags at state changes, so not trusted) |

**Result:** a BERT block draws only 1–5 W more than an awake GPU doing almost nothing. About **93–95%** of a block's measured energy is
"GPU awake × time"; the computation itself is ~5–7%. So for BERT at batch 1 on this machine, CLEAR's component energies (and ours) mostly
measure **duration**. This is why every %Capture gap in section 4 follows time differences.

- Subtracting the session's idle number would not fix this: idle at the start of our runs was 32, 44 or 52 W depending on the state, and
  all are below the awake level (~62 W). Subtracting it makes CLEAR's %Capture worse (8 tokens, 44 W: 83.5% → 71%).
- For Qwen3-8B the GPU draws ~250 W, so the awake base (~62 W) is about a quarter of the energy, and most of it is real work.
